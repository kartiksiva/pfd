# Technical Review Report: Milestone T2.2 (Async Job Execution)
**Project:** Process Documentation Agent (MVP)

**Status:** **GO** (Milestone T2.2 Verified)

---

## 1. Executive Summary
The implementation of the **Async Job Execution Framework (T2.2)** is robust and fully compliant with the project's architectural mandates. The use of FastAPI `BackgroundTasks` provides a lightweight but effective async orchestration layer for the MVP. The system now correctly handles background state transitions, metadata population, and failure persistence.

---

## 2. Review Findings & Verification

### [PASSED] 1. Async Orchestration & Wire-up
- **Verification:** `main.py` successfully integrates `BackgroundTasks` into the `POST /api/jobs` endpoint. Jobs are accepted (202) and immediately queued for background processing without blocking the request-response cycle.

### [PASSED] 2. Processing State Progression
- **Verification:** `worker.py` implements the expected state machine:
  - `queued -> processing` (at job start)
  - `processing -> needs_review` (upon completion of mock pipeline)
- **Metadata Updates:** The worker correctly populates `model_plan`, `usage_cost_estimate`, and the new `progress` object. The `progress` object provides granular stage visibility (`provider_routing`, `processing`, `ready_for_review`), which is critical for the UI.

### [PASSED] 3. Persistence & Schema Integrity
- **Verification:** 
  - `JobRecord` in `models.py` now includes the `progress` JSON column.
  - `repository.py` provides `update_job_metadata` for clean, multi-field updates.
  - `database.py` includes the necessary SQLite column evolution logic for the `progress` field.

### [PASSED] 4. Worker Reliability & Error Handling
- **Verification:** The `_set_failure` helper in `worker.py` ensures that if the background task fails (e.g., unexpected exception or invalid transition), the job status is marked as `failed`, and the diagnostic `error_code` and `error_message` are persisted. This prevents "zombie" jobs that stay in `processing` forever.

---

## 3. General Observations & Guidance

### [LOW] Observation: Hardcoded Model IDs
- **Note:** `_resolve_model_plan` uses hardcoded strings (e.g., `gemini-2.5-flash`). While acceptable for MVP development, these should be moved to `config.py` in the next milestone to allow for easier model pinning and rotation.

### [LOW] Observation: Static Cost Estimation
- **Note:** The `usage_cost_estimate` is currently static. This is the correct approach for `T2.2`, but ensure that as `T2.2a/b` (Adapters) are implemented, the logic is updated to reflect actual token usage from provider responses.

---

## 4. Approval for Progression
The project is cleared to proceed to **Milestone T2.2a (OpenAI Adapter)** and **T2.2b (Google Adapter)**.

**Guidance for Adapters:**
- Implement the `Provider` strategy pattern mentioned in previous reviews to keep `worker.py` clean.
- Ensure adapters handle transcription fallbacks as required by the PRD.
- Standardize the "Evidence" schema returned by adapters to ensure `T2.3` (Media Understanding) receives a consistent payload regardless of the provider.
